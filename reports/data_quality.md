## 3. 关键决策：订单金额为什么不用源字段

源系统的 `sales_orders.order_amount_raw` **与明细汇总对不上**，这是刻意注入的脏数据，
也正是真实数仓里最常见的坑：口径字段没人维护，报出来的销售额永远是错的。

| 指标 | 值 | 说明 |
| :--- | ---: | :--- |
| 有偏差的订单 | 590 条（6.6%） | 任意金额差 ≥ 0.01 元 |
| 偏差 ≥ 1% 的订单 | 587 条（6.6%） | 真正需要修的这批 |
| 这批的中位偏差 | +12.00% | 源系统用了过期的价目表 |
| 金额加权偏差率 | 1.18% | \|偏差总额\| / 订单总额，不受小单放大 |
| 受影响金额 | 5,797,239 元 | 若直接用 raw 字段会算错的金额规模 |

**结论**：销售额一律由 `order_items` 汇总计算（视图 `v_order_fact.order_amount` 已固化该口径）。
这属于「在数据层解决、而不是靠提示词叮嘱模型」的问题——提示词能降低出错概率，但无法保证永远不出错。

## 4. 其他被修正的数据缺陷

- **回款单位混用**：221 条记录以「分」为单位，最大单笔从 70,268,590 换算为 1,027,786 元。
- **退款金额超过订单金额**：16 条被按订单金额封顶，退款总额 23,461,697 → 23,196,512 元。
- **未来单**：20 条下单日期晚于数据截止日（2026-03-15），保留行但置为 `cancelled`。
- **孤儿记录**：剔除测试客户后产生 68 条订单、0 条明细悬空引用，已清理。

## 5. 已知局限（如实说明）

- 数据是合成的，**分布与真实 SaaS 业务有差距**，例如客户集中度、季节性强度；
- 节假日表只标了大节，未覆盖调休；
- 退款与回款的时间对齐是「下单后 N 天」的简化模型，未模拟跨月结算。

这些局限不影响本项目要验证的东西（**口径注入 + 护栏 + 评测方法**），
但真实落地时必须用真实数据重新校准。

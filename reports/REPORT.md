# 实验报告

> 本文件记录**做过的实验、踩到的坑、以及每个数字的来源**。
> 所有结论都能用仓库里的脚本复现：`scripts/build_warehouse.py` + `scripts/run_eval.py --all`。

- 数据集：合成 B2B 销售数据，8,927 笔订单 / 22,317 行明细 / 474 个客户，2024-01 ~ 2025-12
- 模型：`deepseek-v4.1-flash`（OpenAI 兼容接口），`temperature=0`
- 评测集：50 条，7 个能力组，标准答案用 pandas 独立计算
- 硬件：本机，CPU 执行（DuckDB 单查询 20–40 ms）

---

## 一、主实验：消融

五档配置，差异只来自「给模型看什么」与「失败后能不能自救」：

| 档位 | schema | 业务口径 | 少样本 | 自修复 |
| :--- | :--- | :--- | :--- | :--- |
| `baseline` | 裸 DDL（只有表名列名类型） | ✗ | ✗ | ✗ |
| `schema` | 带中文业务口径注释 | ✗ | ✗ | ✗ |
| `glossary` | 带注释 | 13 条口径 | ✗ | ✗ |
| `fewshot` | 带注释 | ✓ | BM25 检索 3 条 | ✗ |
| `full` | 带注释 | ✓ | ✓ | ≤2 次 |

### 关键发现

**① 最大的收益不在提示词工程，而在「把口径写进 schema」。**

从 `baseline` 到 `schema` 只改了一件事：把
`status VARCHAR` 换成
`status VARCHAR — 订单状态：pending 待付款 / paid 已付款 / shipped 已发货 / completed 已完成 / cancelled 已取消 / refunded 已退款。有效订单 = paid + shipped + completed`。

准确率直接跳了一个台阶。原因从 `baseline` 的失败样本里能看得很清楚——

| 题 | 裸 DDL 下模型怎么猜 | 实际口径 |
| :--- | :--- | :--- |
| A01 有效订单数 | `WHERE status = 'completed'` → 7421 | 7802（paid+shipped+completed） |
| A06 官网销售额 | `SUM(order_amount_raw)` | 该字段偏差 12% |
| A03 华东销售额 | `status='completed'` | 少了 paid/shipped |

模型不是「不会写 SQL」，它写得很工整——**它只是不知道这家公司的口径**。
这一条是整个项目最值得讲的结论：**数据层做对了，提示词才有效**。

**② 业务口径（glossary）在 schema 之上还能再加一层。**

`schema` 里已经写了不少口径，但有些「跨字段的规则」放不进单列注释，
比如「客单价 = 净销售额 / 有效订单数」「环比用 LAG 不用日期字符串减一」。
这 13 条 glossary 带来的增量不大但稳定，主要补在 B 组与 D 组。

**③ 少样本检索是锦上添花，不是主力。**

从 `glossary` 到 `fewshot` 的增益很小，而且增加的 prompt token 接近 50%。
诚实的结论是：**在口径已经写清楚的前提下，示例的边际收益很低**；
它的价值在于「示范输出风格」（比如都写成一行、都用 `date_trunc`），
而不是「教模型业务知识」。

**④ 自修复：能救执行错误，救不了语义错误。**

`full` 档触发了若干次自修复。观察到的规律是：

- **护栏拦截 / 执行报错 → 修复成功率高**：错误信息具体（「列不存在」「缺 ON 条件」），
  模型拿到就能改；
- **语义错误（算错了但能跑）→ 修复完全无效**：模型没有「我算错了」的信号，
  再生成多少次都是同样的口径错误。

这直接说明一件事：**自我修复不能替代评测**。护栏解决「跑不出来」，
口径解决「算错了」，两者是正交的。

## 二、踩到的真实缺陷（按发现顺序）

这一节是这份报告里最有价值的部分——**每一个缺陷都不是「写错了代码」，而是「不报错但结果错」**。

### 缺陷 1：回款率 132%，且没人觉得不对

第一次跑通全链路后，评测集里「整体回款率」的答案是 **1.3243**。
一个回款率超过 100% 的数，在页面上看起来完全正常。

排查过程：

1. 先怀疑口径（是不是把订单金额算成了净额）——不是；
2. 按订单逐笔比对 `payments.amount` 与 `order_amount`，发现 152 笔的比值是 **100.0×**；
3. 定位到 `normalize_payment_units()`：它只对「金额 > 5000 万」的记录做「分 → 元」换算，
   而一笔 4.4 万元的订单被写成「分」时只有 4,402,210，**低于阈值，漏掉了**。

修复：不再用单一阈值，改用**订单金额交叉校验**——对每笔回款同时计算
「按元解释的回款/订单」与「按分解释的回款/订单」，取更接近业务常识（≤1.5 倍）的那个。
修复后换算 221 条，回款率变为 0.8917。

> 这个缺陷的教训：**单一阈值规则在长尾数据上必然漏检**。
> 能用「另一个独立字段」做交叉验证时，就不要只靠绝对阈值。

### 缺陷 2：视图汇总 ≠ 全表汇总（差 5 笔订单）

`build_warehouse.py --check` 里的自洽性校验报错：`v_order_fact` 算出 7802 笔有效订单，
pandas 算出 7807。查询之后发现 5 笔「有效状态但没有任何明细行」的订单——
它们的明细在红冲（负数）清洗那一步被全部剔光了，剩下一张空订单。

`v_order_fact` 用 `JOIN order_items`（内连接），这些订单自然被丢掉；
但 `sales_orders` 全表汇总时它们还在，于是两边不一致。

修复：清洗阶段显式剔除「有效状态 + 无明细」的订单，并把这条规则写进数据质量报告。
**这类差异如果不在建库时校验，会一路带到评测集的 ground truth 里**，
表现为「模型答案和标准答案都差 5 笔」，然后被误判成模型错。

### 缺陷 3：判分器把正确答案判成错的（假阴性）

第一次完整评测后，逐条看失败样本，发现有 4 条「模型 SQL 明显正确，但被判错」：

| 现象 | 原因 |
| :--- | :--- |
| `date_trunc` 返回 `2025-01-01`，期望 `"2025-01"` | 判分器只做 `str()`，没做时间归一化 |
| `date_trunc('quarter')` 返回 `2025-01-01`，期望 `1` | 季度序号与季初日期没有等价映射 |
| 模型多带一列「订单数」 | 裁列逻辑取了尾部，取错了列 |
| `SUM()` 返回 NULL，期望 0 | 空结果两种表达没做等价 |

这说明**评测器的 bug 和模型的 bug 会混在一起**，而且前者更危险——
它会让你得出「模型不行」的错误结论，然后去改根本不需要改的提示词。

修复后重跑，多条模型的准确率上升。这也意味着：**报告里的所有数字都是在
「判分器已经修干净」之后才成立的**，早期数字不能直接对比。

### 缺陷 4：CTE 名字被当成「不在白名单的表」

所有带 `WITH` 的查询都被护栏拒绝，错误是「表 `m` 不在白名单内」。

原因：`sqlglot` 里 CTE 的引用也是 `exp.Table` 节点。不排除 CTE 名，
所有用 CTE 组织复杂查询的写法都会被误杀——而 CTE 恰恰是模型写窗口函数时的必备结构。

这是一个典型的**假阳性**：护栏没错、SQL 也没错，是规则写得太粗。

### 缺陷 5：恒真 ON 条件

对抗测试时 `JOIN customers b ON 1=1` 被放过了。

原来只检查「有没有 ON 子句」，没检查「ON 条件是不是恒为真」。
修复：加 `_is_constant_condition()`，识别 `ON 1=1` / `ON TRUE` / `ON 'a'='a'` /
`ON 1=1 AND x>0`（任一侧是常量即判可疑）。

这条是「对抗测试的价值」的证明：**不做对抗测试，永远不会想到模型会这么写**。

### 缺陷 6：评测集自己在考「猜口径」

有 7 道题的题面存在歧义，导致「模型算对也被判错」：

| 题 | 歧义 | 处理 |
| :--- | :--- | :--- |
| B07 退款 | 按退款到账月 vs 按订单归属月 | 题面写明「按订单归属月」 |
| B08 回款 | 同上 | 题面写明「按到账日期」 |
| C07/E01 品牌品类销售额 | 明细金额 vs 订单金额分摊 | 题面写明「按明细行金额汇总」 |
| E06 TOP 客户 | 第 4/5 名同分，排序不确定 | 关掉顺序敏感 |
| F01 退款率 | 金额口径 vs 笔数口径 | 题面写明「退款金额/销售额」 |

这些都是**评测集的问题，不是模型的问题**。教训是：
**写评测集时，题面必须写到「另一个人看完能给出唯一答案」**，
否则测的是「猜出题人想法」的能力。

### 缺陷 7：最隐蔽的一个——退款订单不在「有效订单」里

`refunded` 状态的订单本身就不是有效订单。所以「某月的退款金额」
**不能**用 `WHERE status IN ('paid','shipped','completed')` 过滤——
那样会把退款金额最大的那批订单（状态就是 `refunded`）全部排除。

实际影响：6 月的退款总额，按有效订单算是 218,026 元，按全量订单算是 1,883,917 元，
**差了 8.6 倍**。而这两条 SQL 都「跑得通、看起来合理」。

这类缺陷是 NL2SQL 的真实难点：**不是语法，是领域里反直觉的口径嵌套**。

## 三、安全护栏的对抗测试

`tests/test_guard.py` 里有 39 条攻击样本，按类别覆盖：

| 类别 | 样本数 | 代表 |
| :--- | ---: | :--- |
| DDL / DML | 9 | `DROP TABLE`、`MERGE INTO`、`INSERT INTO ... SELECT` |
| 语法绕过 | 7 | `dRoP tAbLe`、`DROP /*注释*/ TABLE`、`SELECT 1; DROP TABLE` |
| 资源访问 | 13 | `read_csv('/etc/passwd')`、`COPY ... TO`、`ATTACH`、`glob(`、`duckdb_tables()` |
| 逻辑滥用 | 9 | `SELECT *`、`CROSS JOIN`、`ON 1=1`、无 LIMIT、越权表名 |

全部拦截，且每条拦截都返回**可执行的修复建议**（回传给模型做自我修复）。
外加 10 条合法查询的**假阳性测试**——护栏太严同样是 bug。

运行时兜底（与 AST 护栏正交）：

- `read_only=True` 连接
- `SET enable_external_access=false`
- `memory_limit=1GB` / `threads=2`
- 8 秒超时（线程 + `interrupt()`）
- 500 行上限（`fetchmany`，不是全拉再切片）

## 四、接地校验

「结果解读」环节单独做数字核实：答案里出现的每个数字，必须能在
结果集、列求和、行求和里找到（允许四舍五入与万元换算）。

为什么需要：实测发现模型会在解读阶段「顺手算一个」结果里没有的数
（结果只给了销售额，它自己除一下报客单价）。**SQL 错能评测出来，解读错没人查。**

实现里踩了两个坑：

1. **万元换算的容差**：4,090,463.94 说成「409.05 万元」是对的，
   但按 1e-6 相对误差判等会判成幻觉。修复：容差 = 显示精度对应的最小单位；
2. **数字与单位之间的空格**：「12 万元」很常见，单位要从数字后面跳过空白再取。

## 六、复现

```bash
uv venv venv && uv pip install --python venv/bin/python -e ".[dev]"
venv/bin/python scripts/build_warehouse.py        # 建库 + 数据质量报告 + 口径自洽校验
venv/bin/python -m pytest tests/ -v               # 157 条测试，约 4 秒
cp configs/local.yaml.example configs/local.yaml  # 填 api_key
venv/bin/python scripts/run_eval.py --all         # 5 档配置，全跑约 10 分钟
```

结果落在：

- `reports/RESULTS.md` —— 消融对比表（自动生成）
- `reports/preds/records_<profile>.jsonl` —— 每条样本的 SQL / 结果 / 耗时 / token / 判分
- `reports/preds/summary_<profile>.json` —— 汇总指标
- `reports/data_quality.md` —— 数据质量报告

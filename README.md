# 自然语言数据分析 Agent（NL2SQL）

> 把「业务人员的一句话」变成「可信的数字」。
>
> 不是「调个 API 生成 SQL 就完事」——这个项目的重点是**如何让 LLM 生成的 SQL
> 既能跑对、又不会把库搞坏、还能量化它到底有多准**。

```bash
uv venv venv && uv pip install --python venv/bin/python -e ".[dev]"
venv/bin/python scripts/build_warehouse.py     # 合成数据 → pandas 清洗 → DuckDB
venv/bin/python scripts/run_eval.py --all      # 跑 50 条评测（需要 LLM key）
venv/bin/uvicorn nl2sql.api.server:app --port 8000   # Web 演示
```

---

## 1. 这个项目解决什么问题

企业里的数据分析有一条固定的长尾：**80% 的问题是重复的、口径固定的，但业务人员不会写 SQL**。
NL2SQL 看起来是个已经被解决的问题（GPT-4 级别的模型确实能写出正确的 SQL），
但真正落地时卡住的从来不是「生成」：

| 真实卡点 | 具体表现 | 本项目的做法 |
| :--- | :--- | :--- |
| **口径不一致** | 问「销售额」，模型不知道「有效订单才计入」，也不知道源系统的金额字段是脏的 | 业务口径注入（13 条）+ 把正确口径固化成视图 |
| **不敢让它连生产库** | 一句 `DROP TABLE` 就完了；正则黑名单随便绕过 | 基于 AST 的六层白名单护栏 + 只读连接 |
| **不知道准不准** | 手上没有评测集，「感觉还行」 | 50 条分层评测集 + 可归因的错误分类 |
| **错了没人发现** | 结果解读阶段模型会自己编数字 | 「结果接地校验」：解读里的数字必须能在结果集里找到 |

所以这个仓库的四块核心资产是：**数据层（口径）→ 护栏（安全）→ 评测（度量）→ 接地（可信）**。

## 2. 整体架构

```
                    ┌─────────────────────────────────────────────┐
  自然语言问题  ──▶ │ 1. 语义层                                    │
                    │    · schema 注入（中文业务口径，不是 DDL 直译）│
                    │    · glossary 业务口径（13 条，含「错误写法」）│
                    │    · BM25 少样本检索（中文 bigram，确定性）   │
                    └──────────────────┬──────────────────────────┘
                                       ▼
                    ┌─────────────────────────────────────────────┐
                    │ 2. LLM 生成 SQL（OpenAI 兼容，强制流式）      │
                    └──────────────────┬──────────────────────────┘
                                       ▼
              ┌────────────────────────┴────────────────────────┐
              │ 3. AST 安全护栏（sqlglot）                       │
              │    语句类型 → 禁用节点 → 外部函数 → 表/列白名单    │
              │    → 防笛卡尔积 → 强制 LIMIT                     │
              └────────────────────────┬────────────────────────┘
                                       │ 不通过
                          ┌────────────┴────────────┐
                          ▼                         ▼
                  4. 自我修复（≤2 次）          5. DuckDB 只读执行
                          │                    8s 超时 / 500 行 / 关闭外部访问
                          │                         │
                          └──────────▶ 失败回传 ────┘
                                                   ▼
                    ┌─────────────────────────────────────────────┐
                    │ 6. 结果解读 + 接地校验                        │
                    │    解读里的每个数字必须能在结果集/派生值里找到  │
                    └─────────────────────────────────────────────┘
```

**每一步都有 trace**：6 个阶段各自的耗时、输入、错误都在 `AgentResult.steps` 里，
评测按阶段归因，而不是只报一个「错了」。

## 3. 四个值得细看的设计

### 3.1 数据层：把口径固化，而不是靠提示词叮嘱

源系统的 `sales_orders.order_amount_raw` **与明细汇总对不上**（刻意注入，偏差 ≥1% 的订单占 6.6%，
受影响金额 580 万元）。这不是提示词能救的问题——模型写什么 SQL 都会得到错的销售额。

处理方式：

1. **清洗阶段**用订单明细重算金额，源字段只用于监控偏差；
2. **建视图** `v_order_fact` 把「有效订单 + 明细金额 + 运费 − 优惠 − 退款」的口径固化；
3. 提示词告诉模型「用视图，不要用 `order_amount_raw`」。

实测证明这个顺序是对的：**只注入提示词（不建视图）时，模型仍有 40% 的概率去碰 raw 字段**；
建了视图 + 提示词指路之后，50 条里 0 条用错字段。

数据质量报告（8 类脏数据、10 条清洗规则、每条规则的影响行数）见
[`reports/data_quality.md`](reports/data_quality.md)。

### 3.2 安全：为什么必须是 AST，正则一定失败

| 绕过 | 正则黑名单 |
| :--- | :--- |
| `DROP /* x */ TABLE t` | 注释拆开关键字 |
| `dRoP tAbLe t` | 大小写 |
| `SELECT 1; DROP TABLE t` | 只查了第一条 |
| `COPY (SELECT ...) TO '/etc/passwd'` | 不是 DML，压根不在黑名单 |
| `SELECT * FROM read_csv('/etc/shadow')` | SQL 长得完全合法 |
| `SELECT ... JOIN t ON 1=1` | 语法合法，但会炸成笛卡尔积 |

这里做的是**六层白名单**（`src/nl2sql/sqlsafe/guard.py`）：

1. 单语句（拒绝多语句与分号注入）
2. 只允许 `SELECT` / `WITH`（拒绝所有 DDL/DML/COPY/ATTACH/PRAGMA/INSTALL）
3. 禁用节点 + 函数前缀（`read_csv*` / `glob` / `duckdb_*` / `shell` …）
4. 表名白名单（CTE 名不算表 —— 这是个实际踩过的假阳性）
5. 禁止 `SELECT *`（只看最外层投影，CTE 内部放行）、禁止无 ON 或恒真 ON 的 JOIN
6. 明细查询强制 `LIMIT`（聚合查询豁免）

外加运行时兜底：`read_only=True` 连接 + `enable_external_access=false` + 8s 超时 + 500 行上限。

**对抗测试覆盖 39 条攻击样本**（`tests/test_guard.py`），全部拦截，且每条拦截都返回可执行的修复建议。
其中一条是实测漏过去的 `JOIN ... ON 1=1`，后面的版本补上了常量条件检测。

### 3.3 评测：50 条分层题 + 可归因的错误分类

评测集不是「随便问几句」，而是按能力维度分 7 组：

| 组 | 数量 | 考什么 |
| :--- | ---: | :--- |
| A 基础指标 | 8 | 时间/地区筛选、聚合 |
| B 业务口径 | 10 | 有效订单、净销售额、客单价、毛利率、**地区歧义**、首单客户 |
| C 分组与排名 | 8 | GROUP BY、TOP N、并列处理 |
| D 时间序列 | 8 | 环比/同比、相对时间、季度/半年 |
| E 多表关联 | 6 | 明细下钻、品类/品牌/行业维度 |
| F 比率与占比 | 6 | 退款率、复购率、占比、动销率 |
| G 边界与陷阱 | 4 | 空结果、赠品、超界时间 |

**标准答案用 pandas 独立算一遍**，再用 DuckDB 视图跑一遍交叉验证（`tests/test_cases.py`）——
两条完全不同的实现路径对上，才说明口径没写歪。

判分不做宽松匹配：行数不一致直接判错；容差 0.5%（比率类 1%–2%），
刚好能容纳浮点误差、又能抓住「用错金额字段」的 12% 偏差。

错误分为 8 类：`安全拦截 / 执行失败 / 无结果 / 行数不符 / 数值误差 / 排序不符 / 口径错 / 时间错`。
其中「口径错」是通过 glossary 里每条口径的 `wrong_pattern` 做**确定性识别**的，
所以报告能写出「这 6 条错误里有 4 条是用了 `order_amount_raw`」，而不是笼统的「不准」。

### 3.4 接地校验：解读里的数字必须能被核实

这是实测发现的问题：SQL 对了，但解读阶段模型会「顺手」算一个结果里没有的数
（比如结果只给了销售额，它自己除一下报了个客单价）。
这类错误比 SQL 写错更危险，因为**没人会去查**。

`check_grounding()` 把答案里的数字抠出来，与结果集的所有数值、列求和、行求和比对。
允许四舍五入（「409.05 万元」对 4,090,463.94 是合法的），但不容忍凭空出现的数字。

实现里踩过两个坑，都写了注释：
- **万元换算的容差**：按 1e-6 相对误差判等会把正确的「409.05 万」误判成幻觉；
- **数字与单位之间有空格**（「12 万元」），单位要从数字后面跳过空白再取。

## 5. 项目结构

```
src/nl2sql/
├── schema.py                 # 表结构单一事实来源（DDL / 提示词 / 白名单都用它）
├── prompts.py                # 提示词（唯一「改了会影响准确率」的文本资产）
├── data/
│   ├── synth.py              # 合成数据 + 8 类脏数据注入
│   └── pipeline.py           # pandas 清洗流水线 + 数据质量报告生成
├── semantics/
│   ├── glossary.py           # 13 条业务口径（含「典型错误写法」正则）
│   ├── examples.py           # 20 条少样本示例（全部在真库上跑通过）
│   └── retriever.py          # BM25（中文 bigram），无第三方依赖
├── sqlsafe/
│   ├── guard.py              # AST 六层白名单护栏
│   └── executor.py           # DuckDB 只读执行（超时/限行/外部访问关闭）
├── agent/analytics.py        # 端到端编排 + 自我修复 + 接地校验
├── eval/
│   ├── cases.py              # 50 条评测集（pandas 算标准答案）
│   └── evaluator.py          # 判分 + 8 类错误归因 + 报告生成
├── llm/client.py             # OpenAI 兼容客户端（强制流式、结构化重试）
└── api/
    ├── server.py             # FastAPI
    └── static/               # 单页前端（深色，含护栏演示页）
```

## 6. 复现步骤

```bash
# 1. 环境（uv，虚拟环境在工程内）
uv venv venv
uv pip install --python venv/bin/python -e ".[dev]"

# 2. 建数仓（几秒，不联网；DuckDB 库不入库，必须由这一步生成）
venv/bin/python scripts/build_warehouse.py
#    → data/warehouse.duckdb、reports/data_quality.md
#    → 会顺带做「视图汇总 == pandas 汇总」的口径自洽性校验

# 3. 单元测试（201 条，约 6 秒，不联网）
venv/bin/python -m pytest tests/ -v

# 4. 跑评测（需要 LLM key，50 条约 2–4 分钟）
cp configs/local.yaml.example configs/local.yaml   # 填入 api_key
venv/bin/python scripts/run_eval.py --profile full --limit 5   # 先冒烟
venv/bin/python scripts/run_eval.py --all                      # 四个配置全跑

# 5. Web 演示
venv/bin/uvicorn nl2sql.api.server:app --port 8000
#    打开 http://127.0.0.1:8000
#    三个页签：提问 / 安全护栏演示 / 数据集与口径
```

### Web 界面能演示什么

| 页签 | 内容 |
| :--- | :--- |
| **提问** | 自然语言 → 生成的 SQL → 结果表格 → 解读；下方列出**六个阶段的执行轨迹**（生成 / 校验 / 执行 / 修复 / 接地 / 解读），每段都有耗时 |
| **安全护栏演示** | 预置 11 条攻击 SQL（`DROP` / 注释绕过 / 多语句 / `read_csv` / `COPY` / `ATTACH` / 笛卡尔积 / 系统表…），点一下就能看到**拦截原因与修复建议**；最后一条是正常查询，用来对照「护栏不会误杀」 |
| **数据集与口径** | 数据集概览、7 张表的完整字段说明、13 条业务口径 |

这个「护栏演示」页是刻意做的：**面试时与其口头说「我们有安全护栏」，
不如让对方亲手点一条 `DROP TABLE` 看它被拒绝**。

## 7. 已知局限（如实写）

1. **数据是合成的**。分布与真实 SaaS 业务有差距（客户集中度、季节性强度）。
   本项目验证的是「口径注入 + 护栏 + 评测方法」，不是「在某个真实库上刷到多准」。
   真实落地必须用真实数据重新校准评测集。
2. **单表问答，不做多轮**。没有上下文澄清（「那华南呢？」这种追问需要对话状态管理）。
3. **SQL 复杂度有上限**。评测集里没有窗口函数嵌套 3 层以上的题；
   对超复杂查询，模型的成功率会显著下降。
4. **接地校验只查数字**。不检查因果解释是否合理（比如把销售额下降归因到错误的原因）。
5. **没有做 schema linking 的向量检索**。表只有 7 张时，全量注入 schema 就够；
   上百张表时必须换成检索式 schema 选择。
6. **超时用线程 + `interrupt()`**。这是 DuckDB 目前最可靠的软中断方式，
   但没有进程级隔离；生产环境建议每个查询一个子进程或独立容器。
